# 動体展示用 AI 物体検出・アラートシステム 仕様書

- **仕様バージョン:** 0.7.0
- **更新日:** 2026-11-23
- **対象リポジトリ:** [kotadymo/2027-tukuba-exhibition](https://github.com/kotadymo/2027-tukuba-exhibition)
- **状態:** 実装用仕様（Insta360 GO Ultra の接続部分は実機検証が必要）

## 1. 目的と確定事項

展示用 Web アプリケーションとして、**Insta360 GO Ultra のライブ映像**または**アップロードした動画ファイル**を FastAPI で受信・処理し、NVIDIA GPU（CUDA）またはCPU上のカスタムYOLO物体検出モデルで検出する。

React の画面に映像と Bounding Box を表示し、設定された複数の物体クラスが同一フレーム内に存在したとき警告を表示・発音する。**アラートが発報した元フレーム画像と、そのフレームの検出情報を SQLite に記録**し、履歴から再表示できるようにする。保存されたフレームを危険物体の周囲で切り出し、**危険箇所のタップと危険理由2択による教材を自動生成**する。回答履歴は保存しない。

### 1.1 採用する構成

| 項目 | 仕様 |
| --- | --- |
| Backend | Python / FastAPI |
| Frontend | React / Vite（既存リポジトリの JavaScript / JSX 構成を維持） |
| デザイン | Google Material Design 3（M3）のデザインシステム、MUI＋M3テーマを採用 |
| DB | SQLite / SQLAlchemy |
| ライブ映像入力 | Insta360 GO Ultra（Wi-Fi）、[Daiki-Iijima/insta360-go-ultra-sdk](https://github.com/Daiki-Iijima/insta360-go-ultra-sdk) を採用 |
| 動画ファイル入力 | Frontend からアップロードする MP4（H.264 推奨） |
| 入力ソース | `insta360` と `video` の **2 種類を排他的に切り替え** |
| モデル | Ultralytics 互換の物体検出用カスタム `.pt`、Frontend から登録／切り替え |
| 推論 | **NVIDIA GPU（CUDA）／CPU**。Auto（CUDA優先・CPUフォールバック）、CUDA固定、CPU固定を画面で選択 |
| ルール | 同一推論フレーム内に選択した全クラスが存在する（AND）、危険理由マスターを参照 |
| 警告 | React 画面上の警告＋ブラウザでの PC 警告音 |
| アラート保存 | **SQLite の JPEG BLOB＋検出データ＋発報メタデータ** |
| 教材化 | 危険な物体周辺の切り出し静止画、異なる発報イベントから最大3問。**異なる危険理由を優先** |
| 問題 | 正解ボックスをタップ → 危険理由マスターの**正解文／誤答文**で2択 → 解説 |
| 教材の記録 | 元フレームと検出情報・教材メタデータは保持、学習者の回答・得点は保存しない |
| 入力操作 | マウス・タッチパネル両対応 |
| 通信 | REST API（設定・履歴）／WebSocket（映像＋検出＋イベント） |
| 実行 | Backend と Frontend を同じ展示 PC で起動、通常利用はローカルで完結 |

### 1.2 廃止する機能・前提

- **Raspberry Pi／reCamera カメラへの接続は廃止。**
- カメラ入力における RTSP 接続設定、RTSP 接続 API、RTSP 再接続処理、カメラアダプターは**初期実装対象外**。
- Raspberry Pi はカメラ中継機としても**必須としない**。展示 PC を GO Ultra の Wi-Fi に直接接続する構成を基本とする。
- 既存の**動画アップロード・再生モードは維持**する。

デモ専用のため、ログイン／権限管理、API 認証、アクセス制限、監査ログ、モデルのハッシュ検証等は実装しない。モデルは展示担当者が出所を把握しているファイルを使用する。`.pt` のロードには任意コード実行の危険があり得るため、信頼できるモデルのみを使用する運用とする。

## 2. 全体アーキテクチャ

~~~text
[Insta360 GO Ultra]          [アップロード MP4]
  │ カメラの Wi-Fi                │ REST アップロード
  │ 独自 TCP + H.265             ▼
  ▼                         data/videos/
  [非公式 SDK アダプター]         │
  [FFmpeg H.265 デコード]       [動画デコード]
              └──────────┬─────────┘
                         ▼
                  SourceService
             （入力モード切り替え）
                         │ 最新フレーム
                         ▼
                InferenceService
               カスタム YOLO / CUDA または CPU
                         │ 同一フレームの検出結果
                         ▼
                    RuleEngine
                AND / 継続 / 解除
                 [HazardReasonMaster]
                 正解・誤答・解説
                         │ アラート発報イベント
                         ▼
                   AlertService
                JPEG + 検出情報を
                   SQLite に保存
                         │
     ┌───────────────────┴──────────────────┐
     ▼                                      ▼
  WebSocket                              REST API
  画像＋ボックス＋警告                   設定／履歴／画像
     └───────────────────┬──────────────────┘
                         ▼
                    React Frontend
            ライブ表示／動画再生／ルール／
            モデル管理／アラート履歴
~~~

YOLO、ルール判定、履歴保存は入力ソースに依存しない共通サービスとする。入力ソース固有の接続・デコード処理は独立モジュールに隔離する。

## 3. Insta360 GO Ultra ライブ入力

### 3.1 採用する非公式ライブラリと前提

**採用ライブラリは次の公開リポジトリで確定**とする。

- **[Daiki-Iijima/insta360-go-ultra-sdk](https://github.com/Daiki-Iijima/insta360-go-ultra-sdk)**
- 参考資料: [README](https://github.com/Daiki-Iijima/insta360-go-ultra-sdk/blob/main/README.md) / [通信仕様](https://github.com/Daiki-Iijima/insta360-go-ultra-sdk/blob/main/docs/protocol.md)

同リポジトリの説明では、GO Ultra の Wi-Fi アクセスポイントに接続し、**TCP 6666 番ポートの独自プロトコル**で映像を取得する。映像は **H.265 / HEVC Annex B** 形式で、Python スクリプトが動画バイト列を標準出力へ流せる。これは **RTSP ではない**。

次は**採用 SDK の公開情報に基づく設計値**であり、実機動作の保証ではない。

| 項目 | 初期方針 |
| --- | --- |
| カメラ側ネットワーク | GO Ultra が提供する Wi-Fi に展示 PC が接続 |
| カメラ IP | `192.168.42.1`（SDK 記載の例、実機で確認） |
| 制御・映像 | TCP `6666` / 独自 Protocol Buffers |
| 映像形式 | H.265 / HEVC |
| デコード | FFmpeg を介して動画フレームを取得 |
| 実装方法 | 非公式 SDK の映像受信処理を `Insta360Source` にラップする |

**非公式ライブラリは `Daiki-Iijima/insta360-go-ultra-sdk` に確定。** ライセンス条件・利用手順、GO Ultra 実機ファームウェアとの互換性、および展示 PC での動作は実装時に確認する。SDK の README にある動作確認は macOS／Raspberry Pi OS と特定ファームウェアであり、Windows での動作を確認できたわけではない。必要な対応はこの SDK のアダプター層で実施する。

### 3.2 接続フロー

1. 展示 PC で GO Ultra の Wi-Fi に接続する（OS 側の接続操作）。
2. Frontend の入力ソースを「Insta360 GO Ultra」に切り替える。
3. 「接続」ボタンで Backend から非公式 SDK アダプターを開始する。
4. Backend がカメラの制御接続を確立し、ライブプレビューを開始する。
5. 受信した H.265 ストリームを FFmpeg でデコードしてフレーム化する。
6. SourceService が最新フレームを YOLO 推論へ渡す。
7. Frontend に JPEG フレームと Bounding Box を送信する。

カメラ Wi-Fi への切り替えは**基本的に OS 側で行い、Frontend からの Wi-Fi SSID 設定や自動参加は初期版では提供しない**。カメラ Wi-Fi 接続中は PC のインターネット接続がなくなる場合があるが、Frontend と Backend は `localhost` で動作できるようにする。

### 3.3 接続状態と操作

Frontend に以下を表示する。

- 接続状態: `disconnected` / `connecting` / `connected` / `error`。
- 動画プレビューの表示、推論 FPS、最終フレーム受信時刻。
- 「接続」「切断」ボタン。
- エラー内容（Wi-Fi 未接続、接続失敗、ストリーム停止、デコード失敗等）。

切断時は一定間隔（初期値 3 秒）で再接続を試行する。ユーザーが明示的に「切断」した場合は自動再接続しない。切断を検知した際は最新検出状態・ルール判定状態をクリアし、前の映像を正常動作中のように表示しない。

### 3.4 フレーム処理

- ライブ入力と推論は非同期に動作させる。
- 推論待ちキューは最大 1 フレーム、CPU が追いつかないときは古いフレームを捨てる。
- **推論したフレームと、そのフレームで検出した Bounding Box を同期して送る。** 初期版では表示 FPS は推論 FPS に準ずる。
- カメラのタイムスタンプを取得・復元できない場合、Backend の受信時刻／単調時計を使う。タイムスタンプの出典は保持し、異なる時計系を混ぜない。
- エラーや接続再試行は展示 UI に反映する。
- 初期版ではカメラ内録画・撮影コマンド・カメラ内ファイル一覧・バッテリー制御等は使用しない。

## 4. アップロード動画入力（維持）

### 4.1 登録・管理

- Frontend から MP4 動画をアップロードし、Backend の `data/videos/` に保存する。
- 初期対応は MP4（H.264 推奨）。デコード不能な動画はエラー表示。
- ファイルサイズ上限の初期値は 1 GiB。
- 登録時に OpenCV / FFmpeg で解像度、FPS、長さ等を検査する。
- 動画一覧から選択・削除できる。再生中の動画は削除できない。
- アップロード直後は選択状態とし、**再生開始はユーザー操作**とする。

### 4.2 再生操作

- 再生／一時停止／停止／先頭から再生。
- ループ再生は初期値 ON。OFF のときは末尾で停止。
- 再生状態、動画名、動画内時刻・総時間を表示。
- 元動画音声、シーク、再生速度変更は初期スコープ外（アラート音声のみ再生）。

### 4.3 推論との同期

- Backend が動画をデコードし、動画のフレームを**共通の InferenceService / RuleEngine** へ渡す。
- 元動画を Frontend だけで再生してボックスを重ねる構成は採用しない。
- 動画内時刻を基準に原則 1 倍速相当を目指す。CPU が間に合わなければフレームを間引き、遅延蓄積を防ぐ。
- 一時停止時は最後のフレーム／ボックスを残し、新規アラートを発報しない。
- 再開・停止・先頭から再生・ループ先頭・入力切り替え時に、ルールの継続判定状態とクールダウンをリセットする。
- すでにアラートとして**SQLite に保存したフレームは停止・ループ後も残す**。

## 5. モデル登録・NVIDIA GPU / CPU 推論（v0.7.0改訂）

### 5.1 モデル管理

- 既存のUltralytics互換 `.pt` のアップロード・検証・複数登録・有効化・未使用モデル削除を維持する。
- 常時1モデルを実行する。モデル切り替え失敗時は旧モデルを維持する。
- モデル・デバイスの切り替え成功時は古い検出フレーム、推論キュー、ルールの継続判定状態をクリアする。
- アップロード時はCPUで読み込み・ダミー推論を確認。使用デバイスへのロードは有効化・切り替え時に検証する。

### 5.2 推論デバイス選択

設定画面に**Auto（初期値）／NVIDIA GPU（CUDA）／CPU**の3択を追加する。

| 要求設定 `requested_device` | 動作 | エラー対応 |
| --- | --- | --- |
| `auto` | `torch.cuda.is_available()` が真なら `cuda:0`、そうでなければ `cpu` | CUDAロード・推論失敗時は一度だけCPUへフォールバックし、その理由を画面表示 |
| `cuda` | NVIDIA GPUの1台目 `cuda:0`を明示使用 | CUDA未使用可能・メモリ不足時は明確なエラー。**黙ってCPUへ切り替えない** |
| `cpu` | CPU固定 | CUDAを使用しない |

- **要求設定はSQLiteへ保存するが、実際の`effective_device`（`cpu` / `cuda:0` / `none`）はランタイム管理**とする。`auto`選択時のCPUフォールバックも設定値は`auto`のままとする。
- CUDA利用可否、NVIDIA GPU名、要求設定、実効デバイス、フォールバック理由をFrontendに表示する。
- 自動フォールバックを繰り返す無限ループは避ける。再試行は明示的な設定変更やモデル再有効化で行う。
- デバイス切り替え時は推論停止→モデルの移動／再ロード→ダミー推論確認→再開を直列で行い、FastAPIイベントループをブロックしない。失敗時は旧設定・旧モデルへ戻せる範囲で復旧し、状態を表示する。
- NVIDIA GPUの複数枚同時処理、CUDAデバイスの複数選択、TensorRT、量子化・FP16強制は対象外。
- GPUが利用できないPCでも`auto`と`cpu`でアプリが正常に起動する。CUDA対応PyTorchやドライバーの導入方法はREADMEに記載する。

### 5.3 推論設定

| 項目 | 初期値 |
| --- | --- |
| `requested_device` | `auto` |
| `effective_device` | 実行時決定（DB永続化しない） |
| Confidence | 0.40 |
| NMS IoU | 0.70 |
| `imgsz` | 416 |
| 目標推論FPS | 5（暫定、GPU時にも変更可） |
| Batch | 1 |

推論結果のフレームID、画像ピクセル基準のBounding Box、クラス名・ID、Confidence、動画位置、同フレーム同期方式は継続する。GPU/CPUの違いは推論サービス内部に閉じ込め、後段のアラート・SQLite保存・教材生成を共通化する。

## 6. アラートルールと危険理由マスター（v0.7.0改訂）

### 6.1 危険理由マスター（新機能）

各ルールに危険理由を直接記述する方式を廃止し、**正解・誤答・解説を1セットとする独立した危険理由マスター`hazard_reasons`**を導入する。

| フィールド | 例 | 説明 |
| --- | --- | --- |
| `id` | 1 | 理由ID |
| `name` | 手袋の巻き込み危険 | 管理用タイトル |
| `correct_reason` | 手袋が回転部に巻き込まれるおそれがあるため | 2択の正解文 |
| `wrong_reason` | 工具の温度が低くなるため | **手動登録する誤答文** |
| `explanation` | 回転部への手袋の巻き込みに注意する必要があります。 | 回答後の解説 |
| `enabled` | true | 新規ルールでの選択可否 |

- すべての文章は空文字を禁止。**正解文と誤答文は、前後空白・連続空白の正規化後に一致する場合は登録不可（422）**。
- マスター間で正解文の重複が生じないように入力時検証する。誤答文が現実の画像にも正しい可能性は残るため、管理画面で2択プレビューを表示し、登録者が教育上の妥当性を確認する。
- **`glove + bench_drill_handle` と `glove + bench_drill_chuck` など同じ危険を表すルールは同一理由IDを参照**する。理由文の重複登録は不要。
- マスターの一覧・登録・編集・有効/無効化・削除を行う。参照中マスターの削除は409として禁止し、必要なら無効化する。既存ルールが参照するマスターを無効にしてもルールの検知・教材はすぐに止めない。
- 理由マスターの編集は新しい発報に反映する。**既存アラートに保存した正解・誤答・解説のスナップショットは変更しない**。

### 6.2 ルール管理

- ルール名、異なる2種類以上の検出クラス、ON/OFF、成立時間、解除時間、クールダウンを設定する。
- 教材付きルールは`education_target_class_name`（タップする正解クラス1種類）と`hazard_reason_id`（共通マスターへの参照）を持つ。
- 正解クラスはそのルールの必要クラスのいずれか。理由マスター未設定の従来型ルールは検知可能だが教材生成対象から除外する。
- 1ルールに紐づく理由は1件。1つの理由マスターに複数ルールを紐づけてよい。
- 物体間の接触や装着状態は判断せず、同一フレームに指定クラスが共存するAND条件を維持する。

### 6.3 アラート判定

`idle`→`pending`→`active`。2推論フレーム以上、初期0.5秒継続で1回発報。2秒不成立で解除、10秒のクールダウンを維持する。ライブ時刻と動画内時刻の扱いは従来どおり。入力・モデル・デバイス切替時は過去の状態をリセットする。発報時は元JPEG・全検出・理由マスターのスナップショットを保存する。

### 6.4 編集中のルール一覧（新機能）

- 編集フォームで対象ルールを開いたら、**そのルールだけ下部一覧から一時的に非表示**とする（DBからは削除しない）。
- 保存成功・キャンセル時はフォームを閉じ、対象ルールを一覧へ戻す。失敗時は入力値とフォームを保持。
- 別のルール編集に移るとき、未保存変更があれば破棄確認を行う。
- 新規追加フォームを開いたときは既存ルール一覧を隠さない。
- 「登録ルール総数」はフィルター後の表示件数ではなく全件数を表示する。

## 7. アラートフレーム・検出情報の SQLite 保存

### 7.1 保存対象

発報時に同一フレームの元JPEG BLOB（Bounding Boxを焼き込まない）、検出された全クラス・Confidence・BBox、モデル・入力・ルール・発報日時を1つのDBトランザクションで保存する。

**教材付きルールでは、理由マスターID、正解理由、誤答理由、解説、正解ターゲットの検出IDと切り出し範囲をイベントごとにスナップショット保存する。** マスターやルールの後日変更が過去の教材に影響しないようにする。

同じ画像フレームで複数ルールが発報した場合、`alert_frames`には**元画像を1枚だけ保存**し、複数`alert_events`から同じフレームを参照する。動画では`video_id`と`media_time_ms`も保持する。

### 7.2 書き込み・参照

- `source_session_id + frame_id`を一意化。BLOB・検出・イベントは1トランザクション。
- SQLiteのWALモードを使用し、保存処理が推論を長くブロックする場合は専用ワーカーに切り出す。
- 保存エラーでも検出と映像表示は継続。警告をUIに表示し、保存に成功した場合のみ履歴IDを確定扱いにする。
- 履歴画面で元画像とその時点の全BBoxを再描画。JPEGダウンロード可能。
- 教材用の切り出し画像は要求時に生成し、追加のJPEG BLOBは保存しない。
- 学習者の回答・正誤・点数・進捗は保存しない。
- 自動削除は行わず、確認ダイアログ後に全履歴を削除可能。

## 8. Frontend 画面仕様（v0.7.0改訂）

### 8.1 ダッシュボード

- Insta360ライブ／MP4動画の入力切り替え、再生・一時停止・停止・ループ。
- 同じ推論フレームの画像とBounding Boxを表示。クラス名・Confidence・アラート対象の強調。
- **要求推論モード／実効デバイス／CUDA利用可否／GPU名／CPUフォールバック理由／FPS**を表示。
- 検出アラートの警告・ブラウザ警告音、履歴への導線。
- **テストアラートは約4秒後に自動消去**（手動で閉じることも可能）。SQLiteへは記録しない。

### 8.2 危険理由マスター管理（追加）

- 一覧、新規登録、編集、有効／無効化、未参照マスターの削除。
- **名称・正解理由・誤答理由・解説文**を1セットとして入力し、2択プレビューを表示。
- マスターの参照ルール数を表示する。正解理由と誤答理由が同文なら保存できない。
- 「グローブ＋チャック」「グローブ＋ハンドル」などのルールが**同一理由ID**を選択できる。

### 8.3 ルール管理（編集フォーム重複表示の修正）

- 編集フォームを開いたルールは**下部のルール一覧から一時非表示**にする。他ルールは表示。
- 保存成功・キャンセルで該当ルールを一覧に戻す。保存失敗時は入力内容を維持する。
- 別ルールの編集へ移る場合は未保存変更の破棄を確認する。
- 新規追加フォームでは既存ルール一覧を変更しない。総ルール数は表示行ではなくDBの全件数とする。
- 教材設定欄では正解タップクラスと危険理由マスターを選択。直接理由・解説を書き込む旧UIは廃止。

### 8.4 その他画面

- モデル管理：`.pt`アップロード、選択、切り替え。
- 推論・表示設定：`Auto / CUDA / CPU`、Confidence、IoU、`imgsz`、目標FPS、音声ON/OFF、表示オプション。
- アラート履歴：保存画像・全検出ボックス・教材スナップショット閲覧、全履歴削除。
- 問題画面：最大3問、正解ボックスタップ、理由2択、解説、完了画面。マウスとタッチに対応。
- 未選択モデル・CUDA使用不能・動画なし・教材なし・Wi-Fi切断などを、実際の状態に合わせて表示する。

### 8.5 フレーム描画競合の修正（レビュー④）

- 現行の非同期`Image.onload`が前後逆に完了すると旧フレームを上書きし得るため、**表示シーケンスIDまたはフレームIDで最新フレームのみ描画可能**にする。
- デコード完了後・描画直前に現行フレームと一致するか確認し、旧処理を破棄する。
- ソース切替・停止・WebSocket切断・モデル／デバイス変更時に保留中の描画を無効化。Object URL等も安全なタイミングで解放する。
- リサイズでも現在のフレームに対応する画像とBBoxだけを描く。

### 8.6 M3の表示改善（レビュー⑥）

- MUI＋Material Design 3のトークンを継続使用。
- 現行CSSの**9〜10pxの文字、29〜31pxのボタン**を点検・改善する。本文14〜16px、補助文字12〜14px以上、タップ領域約48 CSS px以上を目安とする。
- 警告は色だけに依存せず文章とアイコンを併記し、文字・角丸・余白・状態色を共通トークンに統一する。

### 10.1 データ制約

- `alert_rules.hazard_reason_id`は`hazard_reasons.id`への外部キー（教材未設定ならNULL）。理由マスターが参照中の間は削除禁止。
- 危険理由マスターの正解文・誤答文の正規化比較を実施し、一致を拒否する。
- 発報時にマスターID・**正解／誤答／解説のすべて**をイベントへスナップショット保存し、後からマスターを編集しても既存教材が変わらないようにする。
- 同一`(source_session_id,frame_id)`は元画像1件。複数イベントから参照可。検出・フレーム・イベントは1トランザクション保存。
- `requested_device`のみDBで永続化。`effective_device`は起動環境によって変わるため保存しない。
- 学習者回答・得点・進捗・タップ位置は保存しない。

### 10.2 DB初期化方針

**デモ用途のため旧v0.6.0 SQLiteを初期化して新スキーマを作成してよい。旧ルールの危険理由文を自動移行する必要はない。**

- **起動のたびにDBを消すことは禁止。** 既存DBが古い場合は初期化の必要性を画面／ログで明示し、READMEの手順に従い担当者が明示的に初期化する。
- `data/app.db`を消すとアラートJPEG、検出情報、履歴、ルール、モデル／動画の登録メタデータを失う。必要なら削除前にDBを別名で保存する。
- `data/models/`・`data/videos/`の実ファイルは自動削除しない。ただしDB初期化後はファイルを再登録しなければ一覧に戻らない。
- 新スキーマは初回起動時に生成する。旧新スキーマを混在させず、初期化方法をREADMEに明記する。

## 11. 非機能要件

### 11.1 性能

- CPU 推論の初期目標は **5 FPS**、`imgsz=416`、`batch=1`（実測により調整）。
- H.265 デコードと YOLO 推論を連続処理できるよう、受信・デコード・推論・配信を分離する。
- 処理が追いつかないときは古いフレームを間引き、表示とボックスの**同期を優先**する。
- スナップショット JPEG 圧縮と SQLite 保存がライブ表示を長時間ブロックしないよう、保存をバックグラウンドワーカーに委譲してよい（ただし保存完了前に結果を確定扱いしない）。
- JPEG BLOB のため SQLite ファイルが増大する。展示前に容量を確認する。

### 11.2 安定性

- GO Ultra 切断時の再接続、動画末尾／破損ファイルの処理、WebSocket 自動再接続。
- モデル切り替え失敗時の旧モデル維持。
- DB 保存失敗は明示し、推論を継続する。
- 設定・モデル・動画一覧・ルール・履歴は Backend 再起動後も維持する。
- 実機で **30 分以上**の連続動作試験を行う。

### 11.3 初期版の対象外

Raspberry Pi／reCamera／RTSP 入力、複数カメラ、複数モデル同時推論、GPU 推論、物体追跡、物体同士の接触／距離／位置関係、ROI、常時録画、アラート前後の動画クリップ保存、動画再生位置シーク、元動画の音声再生、カメラ内録画操作、外部ブザー、クラウド通知、ログイン／認証は対象外。

## 16. 教材化・危険予知クイズ（v0.7.0改訂）

### 16.1 教材生成フロー

1. 危険検知・発報時に、元JPEGと全検出ボックスを保存。教材付きルールでは**正解対象検出ID・理由マスターID・正解文・誤答文・解説・切り出し矩形**をイベントへスナップショット保存。
2. 「問題に挑戦」画面では**異なるアラートイベントから最大3問**を一時生成し、問題セットを開始時に固定する。
3. 危険な物体と条件に含まれる他物体を包含する矩形に約25%の余白を付けて切り出した静止画を表示する。元JPEGはDBに1回だけ保存し、切り出し画像は表示要求時に生成する。
4. 初期表示ではBounding Box非表示。ルール指定の正解クラスに属する代表ボックス（Confidence最大の1個）をマウス／タッチで選択できたら成功。**外側のタップは無反応**、不正解の文字や回数は表示しない。
5. 成功時は正解ボックスを表示し、**発報時の危険理由マスターから保存した正解文と誤答文**を2択で表示。選択肢の表示順をランダム化する。
6. どちらを選んでも正しい理由と解説を表示し、次の問題へ進む。すべて終了したら完了画面を表示する。
7. 0問なら教材がない画面、1～2問なら存在する件数だけ出題。学習者の名前・回答・タップ位置・得点・進捗はSQLiteに保存しない。

### 16.2 2択生成と理由の共有

- **他ルールの正解理由を不正解選択肢に使う方式は廃止**する。
- `quiz_correct_reason_snapshot`と新設`quiz_wrong_reason_snapshot`の2つを表示する。正解／誤答が同文にならないよう、マスター登録時とイベント出題時に検証する。
- 同じマスターIDを参照するルールA（手袋＋ハンドル）・ルールB（手袋＋チャック）は同じ理由ペアを使用できる。別の理由を無理に作らない。
- 2択はセット生成時に一度シャッフルして固定し、途中で表示順が変わらないようにする。
- どちらの理由もその画像に当てはまる問題を防ぐため、**マスター作成者が登録時に2択をプレビューして確認**する。AND判定だけで危険な行為を証明できないことも説明する。

### 16.3 出題選定：異なる理由を優先、足りなければ同じ理由

- 最大3問、**異なるアラートイベントID**、**同一セット内でフレームIDの重複なし**。
- まず危険理由マスターIDが異なるイベントを優先し、可能なら直近・異なるルールを採用する。
- 3問に満たなければ**同じ理由マスターIDの別アラートイベント**から補う。同じフレームは使わない。
- 1種類の理由しか登録されていなくても、異なるイベントが3件あれば最大3問作れる。
- 必要なJPEG、ターゲット検出、切り出し領域、正解・誤答・解説スナップショットのあるイベントのみ採用する。未設定のルールは候補から除外。
- 画像が似る場合はできる範囲で別時刻・別ルールを優先するが、新しい画像類似度AIは導入しない。

### 16.4 保存画像の読み込み最適化（レビュー③）

- **クイズ生成時に全イベントのJPEG BLOBを含むORMオブジェクトを一括読み込みしない。**
- `alert_events`と`alert_frames`の**ID・理由ID・サイズ・正解検出ID・切り出し座標等のメタデータだけ**を新しい順に取得する。画像BLOBは遅延ロードまたは取得対象から除外する。
- 候補は例えば100件単位でページングし、上限を設ける。最終的に採用した0～3問に必要な画像だけ`GET /api/quiz/questions/{id}/image`で読んで切り出す。
- 1,000件程度の履歴で、生成時のDB読み込みが全JPEG容量に比例して膨らまないことを確認する。

### 16.5 座標・タップ判定

- `alert_events.quiz_target_detection_id`に実際の検出ID、`crop_x1/y1/x2/y2`に元画像座標を保存。
- 切り出し後は座標を相対化し、画面の`object-fit:contain`による余白・拡大率を補正してPointer Eventsで判定。マウスとタッチ両対応。
- 小さすぎる正解領域は画像の拡大・出題除外を検討。成功時だけBBoxを重ねる。

### 16.6 クイズAPIと非保存

- `POST /api/quiz/generate` は`{"max_questions":3}`（1～3）を受け取り、最大3件の`alert_event_id`、画像URL、切り出し画像サイズ、正解BBox、2選択肢、正解選択肢ID、説明、`hazard_reason_id`を返す。
- `GET /api/quiz/questions/{alert_event_id}/image` は切り出したJPEGを返す。
- 問題・回答・正誤・進捗はReactの一時状態のみで持つ。バックエンドへ回答送信しない。

## 17. デザインシステム：Google Material Design 3

### 17.1 基本方針

アプリ全体を**Google Material Design 3（M3）**のデザインシステムで統一する。

- React JSX との親和性を重視し、UI 基盤は**MUI（`@mui/material`、`@mui/icons-material`）**とする。
- MUI は Material Design を取り入れるが、コンポーネントによっては Material Design 2 の設計を含む。**M3の厳密なピクセル同一性をMUI標準だけで保証するものではない。** M3のトークンでテーマを調整する。
- Google の `@material/web` は M3 を直接実装する Web Components だが、公式リポジトリはメンテナンスモードと明記されているため、今回の React デモではMUIを優先する。
- デザイントークンと MUI テーマを `frontend/src/design/` に集約し、画面ごとの独立した色・余白定義を避ける。
- 参考: [Google Material Design 3](https://m3.material.io/) / [Material UI](https://mui.com/material-ui/) / [Material Web](https://github.com/material-components/material-web)。

### 17.2 コンポーネントとトークン

| 観点 | 基準 |
| --- | --- |
| 配色 | M3 `primary`、`secondary`、`surface`、`onSurface`、`outline`、`error` の意味で定義 |
| 警告 | 危険は `error` 系トークン＋文字・警告アイコンを併用し、赤色だけで意味を伝えない |
| 文字 | M3 display/headline/title/body/label の階層、日本語が読みやすいシステムフォント |
| 余白 | 4/8px 基本グリッド、カード・フォーム・モーダルの余白を共通化 |
| 形状 | M3の角丸トークン、カード・ボタン・ダイアログで一貫性を保つ |
| 入力 | マウス・タッチ共通。操作ボタンは原則48 CSS px以上のタップ領域を目安 |
| 状態 | 接続中・失敗・保存成功・ロード中・教材不足などの共通表示を用意 |
| アニメーション | 正解ボックスの短い強調など最小限。`prefers-reduced-motion` を尊重 |

### 17.3 画面一覧と導線

1. **ダッシュボード:** GO Ultra / 動画入力、YOLO Bounding Box、アラート表示。
2. **問題に挑戦:** 問題進捗（例: 1/3）、大きな切り出し画像、危険箇所タップ、理由2択、解説、完了画面。
3. **アラート履歴:** 発報イベント一覧、画像＋検出ボックス詳細、画像ダウンロード。
4. **モデル管理:** カスタム YOLO `.pt` 登録・切り替え。
5. **設定:** カメラ・動画・推論・アラートルール管理。

**クイズ画面は画像を大きく表示する専用レイアウト**とし、管理画面の情報を詰め込まない。必要な操作以外を目立たせず、手順と進行状況を分かりやすく示す。

## 18. 設計上の改善提案・採用方針

1. **教材スナップショットの不変性（採用）:** 発報時の正解検出ID・危険理由・解説をイベント単位で保存し、後でルールを編集しても既存教材が変わらないようにする。
2. **画像の二重保存をしない（採用）:** SQLiteに元JPEGを1回だけ記録し、危険箇所を切り出した教材画像は要求時に作る。
3. **同じ画像の重複出題を避ける（採用）:** 1セット内で同じ `alert_frame_id` は使わず、可能なら異なるルール・発報時刻を優先する。
4. **理由選択肢不足の明確化（採用）:** 理由が異なる別ルールがなければ2択は構成できない。最低2種類の理由を事前登録し、不足時は出題できない理由を表示する。
5. **危険判定の意味を誤解させない（運用で対応）:** 現行ルールはクラス共起であり、装着・接触を直接認識しない。教材の文章が実際の撮影映像と一致することを展示前に確認する。
6. **操作しづらさの回避（採用）:** 正解のボックスが小さい場合は画像を拡大可能にする。過度に小さい対象を出題から外す。必要なら将来「ヒント表示」を追加するが、タップ成功条件は維持する。
7. **開始時の教材固定（採用）:** セットの途中で新しいアラートが発生しても問題が変わらないようにする。
8. **初回デモの準備（推奨運用）:** 展示開始前に2種類以上の異なる危険理由と複数のアラートイベントを用意し、最初の来場者から問題を体験できるようにする。
